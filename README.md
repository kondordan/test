# Uplift-модель отклика на скидки (целевая метрика — `click_rate`)

ML-пайплайн, который предсказывает, **как клиенты (по `email`) реагируют на скидки**
в письмах. Это задача **uplift-моделирования** (оценка причинного эффекта), а не
обычной классификации:

- **treatment** — в письме была скидка (`"Есть ли скидка в рублях" > 0`) против письма без скидки;
- **outcome** — клик по письму (`click_date` не пустой) → целевая метрика `click_rate`;
- **uplift(x)** = `P(клик | скидка, x) − P(клик | без скидки, x)` — насколько скидка
  меняет вероятность клика для конкретного клиента.

Модель ранжирует клиентов по «отзывчивости на скидку», чтобы скидки можно было
давать тем, кого они реально активируют, и не тратить их на тех, кто кликнул бы и так.

## Данные

В репозитории реальных данных нет, поэтому `src/data_generation.py` создаёт
**синтетический датасет с точно такой же схемой**, как в задаче, с *заданным
причинным эффектом* (гетерогенный uplift, скоррелированный с наблюдаемыми
признаками — историей покупок и размером скидки). Чтобы подключить реальные данные,
просто передайте свои CSV (см. ниже) — схема колонок должна совпадать.

**Таблица коммуникаций:** `email, mailing_name, mailing_date, open_date, click_date,
purchase_date, trip_date, "Есть ли скидка в рублях", claim_sum_usd, adult, pax, state_name`

**Таблица покупок:** `email, date_booking, date_begin, claim_sum_usd, adult, pax, state_name`

## Запуск

```bash
pip install -r requirements.txt
python script.py                                  # синтетические данные (по умолчанию)
python script.py --comm my_comm.csv --purch my_purchases.csv   # ваши данные
```

Результаты складываются в `outputs/`: `metrics_report.json`, `qini_curve.png`,
`uplift_by_percentile.png`, `client_uplift_scores.csv` (uplift на клиента),
`decile_lift_table.csv`, `send_recommendations.csv` (кому слать рассылку).
Обученные модели сохраняются в `models/uplift_ensemble.joblib`.

### Отсечка по дате обучения

Обучение использует рассылки и покупки **строго до 01.06.2026**
(`mailing_date < 2026-06-01`, `date_booking < 2026-06-01`). При этом **сами туры
могут быть на более дальнем горизонте** — поля `date_begin`/`trip_date` (дата
старта тура) НЕ ограничиваются отсечкой. Константа — `CUTOFF` в `script.py`.

### Ансамбль из нескольких моделей

Поскольку для больших файлов включено семплирование, обучается **ансамбль из
нескольких моделей** (`--n-models`, по умолчанию 3): каждая модель учится на своей
случайной подвыборке train (со своим препроцессором), а прогноз — это среднее по
моделям. Это снижает дисперсию от семплирования и переобучение (bagging).

### Сохранение моделей и отдельный скоринг

Ансамбль сохраняется на диск (`models/uplift_ensemble.joblib`, через `joblib`).
Скоринг можно запускать **отдельно**, без переобучения:

```bash
python predict.py                                          # ./data + сохранённая модель
python predict.py --comm comm.csv --purch purchases.csv \
                  --models models/uplift_ensemble.joblib \
                  --out outputs/send_recommendations.csv
```

### Балансировка обучающей выборки (опционально)

Скидки в реальных данных редкие (~0.8%). Чтобы модель «увидела» сигнал
от промо, можно **сбалансировать обучающую выборку**: взять **все** письма с
промо плюс в `--balance-ratio` раз больше писем без промо (по умолчанию ×2).
Флаг включается при запуске и по умолчанию **выключен**:

```bash
python script.py --comm comm.csv --purch purchases.csv --balance              # все промо + 2x без промо
python script.py --comm comm.csv --purch purchases.csv --balance --balance-ratio 3  # все промо + 3x без промо
```

Можно **подобрать ratio автоматически** по CV-Qini — передайте сетку
`--balance-ratios`; перебираются все пары (ratio × модель), выбирается лучшая:

```bash
python script.py --comm comm.csv --purch purchases.csv --balance --balance-ratios "1,2,3,5"
```

В лог выводится таблица перебора, а в `metrics_report.json` пишутся выбранные
`balance_ratio`, `balance_ratio_tuned`, `best_model`.

Балансировка применяется **только к обучающим данным**; **холдаут остаётся в
естественном распределении**, поэтому метрики качества честные. Это андерсэмплинг
класса без промо (все промо сохраняются), что повышает различимость эффекта скидки
при сильном дисбалансе.

> **Про bootstrap по рассылкам.** Отдельный bootstrap (ресэмплинг строк) точность
> прогноза не повышает: он не добавляет информации и не создаёт новых событий
> «промо+клик», т.е. не сужает фундаментальную неопределённость при редком промо.
> Полезный эффект bootstrap (bagging — усреднение моделей по подвыборкам) **уже
> реализован** в ансамбле (`--n-models`); усилить его можно увеличением числа
> моделей. Поэтому отдельный bootstrap-по-рассылкам намеренно не добавлен.

### Прогноз: кому отправлять uplift-рассылку

`send_recommendations.csv` содержит по строке на email:
`email, mean_predicted_uplift, has_upcoming_trip, recommend_send`.

- `mean_predicted_uplift` — средняя по рассылкам клиента предсказанная отзывчивость
  на скидку (ансамбль);
- `recommend_send = True`, если uplift > 0 **и** клиент не исключён;
- **исключаются** клиенты, которые **уже купили тур, но на 01.06.2026 ещё не
  поехали** (есть покупка с `date_booking < cutoff` и `date_begin >= cutoff`) —
  им рассылка не нужна (`recommend_send = False`, `has_upcoming_trip = True`).

Скорятся email, у которых есть хотя бы одна рассылка в данных (для uplift нужен
контекст оффера). Клиентов, которые есть только в покупках, оценить нельзя.

### Логи и отслеживание выполнения

Пайплайн пишет подробный лог в консоль через модуль `logging`: каждый этап
помечается `[START]`/`[DONE]` с таймингом, выводятся промежуточные метрики (баланс
treatment/control, `click_rate`, размеры выборок, Qini по фолдам, метрики холдаута).
При ошибке печатается полный traceback и причина, процесс завершается кодом `1`.

```bash
python script.py --log-level DEBUG          # детальнее (метрики по каждому CV-фолду)
python script.py --log-file outputs/run.log # дублировать логи в файл
python script.py --comm a.csv --purch b.csv --log-file run.log
```

Перед запуском проверяется схема входных таблиц — если не хватает колонки, скрипт
сразу падает с понятным сообщением (например, `communications table is missing
columns: ['click_date']`). Также проверяется непустота выборок, наличие обеих групп
(со скидкой и без) и непустой холдаут.

### Большие файлы и производительность

Чтение и расчёт оптимизированы под большие выгрузки (миллионы строк, «enriched»
файлы с десятками лишних колонок):

- **Читаются только нужные колонки** (`usecols`) — лишние поля enriched-файла не
  грузятся в память; экономия часто в разы.
- **Компактные типы** при чтении: числа → `float32`, низкокардинальные строки →
  `category`.
- **Потоковое чтение по чанкам** (`--chunksize`) с логом прогресса — пик памяти
  ограничен, видно, что процесс идёт, а не завис.
- **Быстрая проверка схемы по заголовку** (без загрузки всего файла).
- **Векторизованный расчёт признаков** через `merge_asof` — без построчного цикла,
  масштабируется на миллионы строк.
- **Отбор модели на сэмпле** (`--max-cv-rows`, по умолчанию 300k) — кросс-валидация
  идёт на подвыборке, а финальная модель дообучается на **полном** train.
- **Bootstrap-CI на подвыборке** холдаута — оценка интервала не зависит от размера.

- **Семплирование при чтении** (`--sample-rows`, по умолчанию 3 млн) — для очень
  больших файлов (десятки/сотни млн строк) в память попадает только равномерная
  подвыборка нужного размера, а не весь файл. Таблица покупок при этом
  фильтруется по отобранным клиентам, поэтому история покупок остаётся полной.
  Для uplift-модели подвыборки в несколько млн строк достаточно (качество и
  доверительные интервалы сохраняются).
- **Ограничение ширины one-hot для категорий** (`MAX_OHE_CATEGORIES`, по умолч.
  50). У реального `mailing_name` могут быть тысячи значений; плотный one-hot тогда
  раздул бы матрицу до десятков ГБ и убил процесс по памяти (это и была причина
  падения на этапе `SoloModel`). Частые категории сохраняются, редкий «хвост»
  группируется в один bucket — память ограничена, а качество не страдает (редкие
  значения почти не несут сигнала, плюс это снижает переобучение). Неизвестные
  при скоринге категории тоже уходят в этот bucket (без ошибок). Матрица —
  `float32`. При необходимости порог меняется через переменную окружения
  `UPLIFT_MAX_OHE_CATEGORIES`.

Проверено: файл 1.28 млн строк / 53 колонки — при `--sample-rows 200000` в памяти
держится ~22 МБ отобранных данных (из 1.28 млн исходных строк), пик памяти ~1.6 ГБ,
Qini на подвыборке совпадает с полными данными.

> Если расчёт «останавливается после чтения», почти всегда дело в размере: файл не
> помещается в память целиком. По умолчанию включено семплирование до 3 млн строк —
> этого хватает. Если памяти мало, уменьшите: `--sample-rows 1000000`. Чтобы
> использовать **все** строки (только если хватает RAM): `--sample-rows 0`.

Полезные флаги для реальных данных:

```bash
python script.py --comm comm.csv --purch purchases.csv \
    --sample-rows 3000000  # размер подвыборки (0 = все строки)
    --sample-frac 0.02     # либо явная доля семплирования
    --sep ';'              # если файл с разделителем ';' (или другим)
    --chunksize 500000     # уменьшить чанк при малой памяти
    --max-cv-rows 200000   # быстрее подбор модели на очень больших данных
```

Семплирование равномерное, поэтому сохраняются: временной диапазон (для
out-of-time холдаута) и баланс групп (со скидкой / без). Для прод-скоринга всех
клиентов обученную модель применяют к данным батчами — обучение на подвыборке
этому не мешает.

Если при чтении ошибка «missing required columns», а в списке найденных колонок
видна одна длинная строка — почти наверняка неверный `--sep` (файл с `;`/табами).
Колонка скидки должна называться ровно `Есть ли скидка в рублях`; если в выгрузке
имя другое — переименуйте её или поправьте `DISCOUNT_COL`/`COMM_*` в коде.

## Как устроен пайплайн

1. **Загрузка + отсечка по дате.** Используются только данные **строго до 01.06.2026**
   (`mailing_date < 2026-06-01`, `date_booking < 2026-06-01`). Туры (`date_begin`/
   `trip_date`) могут быть на более дальнем горизонте и отсечкой не ограничиваются.
2. **Признаки без утечек** (`src/features.py`). Для письма от даты `mailing_date`
   берутся только данные, доступные **строго до** этой даты:
   - агрегаты истории покупок (число покупок, сумма/средний чек, давность, средние
     `pax`/`adult`, был ли уже в стране оффера) — as-of агрегация;
   - вовлечённость по прошлым письмам клиента (expanding open/click rate со сдвигом на 1);
   - признаки оффера/календаря (`claim_sum_usd`, `pax`, месяц, размер скидки в руб.).
   Поля `open_date/click_date/purchase_date/trip_date` текущего письма **никогда** не
   используются как признаки — это будущее/таргет.
3. **Разбиение по времени.** Последние ~4 месяца (`>= 2026-04-01`) — отложенная
   выборка (out-of-time), остальное — обучение. Это честная проверка обобщения.
4. **Выбор модели по кросс-валидации.** Сравниваются мета-обучатели из
   `scikit-uplift`: S-learner (`SoloModel`), T-learner (`TwoModels`),
   Class Transformation; базовые модели — регуляризованный градиентный бустинг и
   логистическая регрессия. 5-fold стратифицированная CV, отбор по среднему Qini AUC.
5. **Финальное обучение и оценка** на out-of-time холдауте.

## Оценка точности прогноза

Для uplift «accuracy» не информативна, поэтому используются профильные метрики:

- **Qini AUC** + **bootstrap 95% доверительный интервал** — основная оценка качества
  ранжирования по uplift;
- **AUUC** (area under uplift curve);
- **uplift@30%** — насколько вырастет `click_rate`, если давать скидку топ-30%
  клиентов по предсказанному uplift, против раздачи всем;
- **Response ROC-AUC** — вспомогательная диагностика предсказания клика;
- **decile lift table** — наблюдаемый uplift по децилям предсказанного uplift
  (валидация, что модель действительно отделяет отзывчивых от неотзывчивых).

CV даёт интервал стабильности, bootstrap — интервал на холдауте; совпадение
порядков величин подтверждает отсутствие переобучения.

## Меры против переобучения

- отсечка по дате 01.06.2026 и **разбиение по времени** (out-of-time холдаут);
- **признаки без утечек** (только прошлое относительно `mailing_date`);
- неглубокие, **регуляризованные** базовые модели с early stopping
  (`max_depth=3`, `l2_regularization`, `min_samples_leaf`, ранняя остановка);
- стратифицированная **кросс-валидация** с отчётом mean ± std и 95% CI;
- честные **uplift-метрики** + bootstrap CI вместо точечной accuracy.

## Структура

```
script.py                 # обучение: данные -> признаки -> CV -> ансамбль -> сохранение -> рекомендации
predict.py                # отдельный скоринг по сохранённой модели (без обучения)
src/data_generation.py    # синтетические данные по схеме задачи
src/features.py           # инжиниринг признаков без утечек
src/uplift_model.py       # препроцессинг, мета-обучатели, ансамбль, save/load, метрики, CV, bootstrap

```

## Применение на реальных данных

В реальной выгрузке скидки, скорее всего, давались **не случайно** (есть смещение
отбора). Тогда перед обучением стоит скорректировать на propensity (IPW/matching)
или использовать в `TwoModels`/`X-learner` корректную балансировку. Для синтетики
здесь назначение скидки рандомизировано (A/B), поэтому uplift идентифицируется
напрямую.
